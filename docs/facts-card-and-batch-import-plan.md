## 一、资料卡片：统一成一种形状，不分大小项目

最早讨论时以为"身高体重"这种客观事实和"《慁》这种大项目"需要两套不同的模板，后来一澜指出其实**不用分**——统一用一张卡：

- **标题**：简短的名字（"情侣水杯""酸辣粉""香港旅行""《慁》"）
- **内容**：自由长文本，支持 markdown 格式排版；客观事实可以完全留空，复杂的项目/长篇可以在这里用 markdown 分段落写"类型/状态/简介/意义/关系记录/我们的话"这些——**不需要单独的固定栏位**，都是同一个 content 字段里用 markdown 组织
- **附件**：可选的照片、可选的链接（婚戒照片、旅行风景照、小说原文文档链接）
- **key类型**：对应 predicate_key，决定这条事实的新旧处理规则（exclusive_current / multi_current / historical_event）
- **关联记忆桶**：证据来源，可能不止一个（见下面"已知缺口"）
- **时间线**：见下一节

这张卡片是骨架层和"未来线/成就册"两边共用的地基——计划完成时弹出来的成就卡，和骨架层里一条事实的详情卡，本质是同一个组件，UI 和后端字段应该共用，不要各做一套。一澜以后如果自建专属前端，也是直接照抄这套卡片结构。

### 时间线的灰色/实色逻辑

- `exclusive_current` 类型：旧记录被新记录取代后，`invalid_at` 会被填上，UI 上这条历史记录显示**灰色**，旁边标注"于XX日期失效"，点开能看到当时的完整内容
- `multi_current` / `historical_event` 类型：不存在"被取代"这回事，所以在时间线上永远是**实色**，不会变灰。偏好类事实（"不喜欢机械化列点表达"这种）大多数属于这一类——它们不需要"从哪天开始生效"这种历史回溯，就是持续性的既定事实

### 数据库层需要新增的字段（还没做，先记录）

在现有 `facts` 表基础上加：
1. **`title`**：短标签，UI 列表页显示这个（跟记忆桶列表一样的展示逻辑）；不同类别在界面上可以把"标题"换成对应说法（旅行类显示成"地点"），这是纯展示层的映射表，不用改数据结构
2. **`content`**：长文本，支持 markdown，可为空
3. **`attachments`**：链接/图片列表，建议存成 JSON 数组（`[{"type": "image"/"link", "url": "...", "label": "...", "source_type": "..."}]`），不用为图片和链接分别开字段。林湛补充：`source_type` 建议区分 `upload`（手动上传）/ `external_link`（外部链接）/ `generated`（AI生成的图，比如以后可能有的插画）/ `bucket_ref`（指向某个记忆桶的入口）——现在不急着做，但字段先留位置，等以后照片/原文链接/生成图混在一起时会更清楚是哪一类来源。

`valid_at` 本来就是可以留空的（不是 NOT NULL），这个不用改，下面会用到。

### 已知缺口：`evidence_id` 目前只能存一个来源 —— 已用关联表解决，见下方第4步里程碑

原计划是把 `evidence_id` 单字符串改成 JSON 数组。第4步实现时林湛建议改用**独立的多对多关联表**（`fact_bucket_links`）而不是数组字段，理由是这样能顺带带上 `relation_type`（evidence/origin/related）和 `note`，以后扩展更方便，不用改字段类型。`facts.evidence_id` 本身没动，继续作为 `add_fact()`/`profile_fact()` 自动写入时的单一溯源字段；新表是资料卡 UI 手动维护的、可能多个的关联，两者并存，互不影响。

## 二、历史批量筛选：三类事实，三种处理方式

核心原则不变（从最早的骨架层方案就定下来的）：**永远只生成候选，不直接写入；查不到/凑不出来的，宁可显示"不确定"或留空，也不能让 AI 自信地编一个假答案**。批量筛选要保的底线不是"每条都精准"，而是"错的时候看得出来是错的，不会被当成真事实堂而皇之地写进去"。

现有基础设施已经有一半——`/api/profile-fact-proposals`（单个记忆桶生成候选）+ `profile_fact()` 工具（确认后同时写入画像事实桶和 facts.sqlite）已经跑通了"AI 生成候选 → 人工确认 → 写入"这条链路，只是目前一次只能对一个桶手动点。"批量"这一层要加的是：自动选一批候选桶、跑完汇总成一份报告，而不是一个一个点。

### 候选桶怎么找：复用 breath() 已有的联想检索，不用另起炉灶

实测过（用真实数据查了"旅行"），breath() 现在的联想浮现机制已经能靠语义关联带出没有字面关键词重合的相关记忆桶（林湛口中"顺着这条线搜索"的效果），这套机制是现成的，批量筛选要用的"怎么把相关记忆桶都找出来"直接复用它就行，不用重新造轮子。

**更新（2026-07-08，两个未验证但值得优先测的假设）**：一澜在Dashboard主搜索框搜"偏好"，发现能搜出一批标签打得很干净的"恋爱偏好/交流偏好"类桶（域=恋爱/内心，标签=亲密接触/恋爱偏好/情感交流等），怀疑类别3（关系/情绪模式类）没有想象中那么无从下手。顺着这个查了代码：

1. **Dashboard主搜索框（`/api/search`）其实已经在搜标签**，不是只搜标题——`bucket_manager.py` 的 `_bucket_lexical_profile` 用 BM25，标题权重3.0、域2.5、标签2.0、正文1.0，标签排第三。但接口写死了 `limit=10`，且标题字面命中还有独立的"词组加分"（最高0.95，标签命中的词组加分上限只有0.54）——如果某个词标题里带的桶本身就有十几二十个，会把打分前十名占满，纯靠标签命中、标题没有这个词的桶排不进前10，看不见。**一澜观察到"搜出来的标题都带这几个字"很可能是这个排序+条数限制导致的假象，不代表标签没起作用。** 没有实测验证，第5步启动时找一个"确定打过标签、但标题绝对不会出现这个词"的词测一次就能证实。
2. **一澜猜测**：现有大部分 `predicate_key`（事实类型）是林湛自己写的，他本人日常在用 breath()，反馈"经常能摸出来一条线"——所以他设计的分类体系本身可能天然贴合 breath() 联想检索的能力边界，类别3的候选查找可能不像理论评估那么无头绪。这是主观反馈，没有量化验证过。

**这两条都不是结论，是第5步动手前第一件该做的验证**：拿几个林湛写的 predicate_key，实测一遍 breath() 联想检索的召回质量；拿一个"标签有、标题没有"的词测一次搜索排序。验证结果会直接影响候选查找该走"复用现成搜索"还是"必须上更贵的语义检索"这条路的判断，比继续纯讨论靠谱。

### 三类事实的时间怎么处理

1. **客观单桶事实**（身高、体重、喜欢的食物……）：如果能精确检索到具体的单个记忆桶，直接用那个桶自己的日期作为 `valid_at`。相对安全，可以批量跑，人工确认的负担较轻。
2. **大项目/长篇**（《慁》、世界观文档）：如果能检索到"开始写""完结""出书"各自对应的桶，这几个天然对应 `historical_event` 模式下的**几条独立记录**（同一个项目、不同的里程碑事件，各自带各自的日期），不用挤在一条里。检索不到某个里程碑的日期就留空，不瞎猜。

   **代表桶数量要设上限**（林湛补充）：像《慁》这种相关记忆桶能轻松有几十上百个，第一版卡片详情页**只挂 1～5 个核心代表桶 + 1 个原文链接 + 1 条补充说明**，不要一次性把所有相关桶都塞进卡片里，那样卡片会变得很重、很难读。需要看更多证据的话，卡片上留一个"查看更多来源"的入口，点开再展开完整列表，不是默认全展示。
3. **关系/语言/情绪模式类**（"讨厌机械列点表达"这种）：这类证据本来就分散在很多次对话里，没有单一的"起点"，`valid_at` 直接用**生成这条总结的日期**（今天），或者干脆留空，不用去凑一个"从哪天开始"的假日期。这类也是最需要谨慎的一类——见下条。

### 关系/语言/情绪模式类：单独的谨慎流程（林湛原话）

> 这最难，不能让 API 自己乱下结论。比如"她讨厌模板句""她害怕被推远""她需要主动哄"。这些要从多次证据里归纳，但必须带证据、带置信度、人工确认。最好先提候选句，不直接写成最终事实。

跟其他两类共用同一张资料卡（标题+内容），但生成候选这一步要走比其他两类更保守的流程：多条证据 + 置信度 + 人工确认，不能一步到位自动生成"最终事实"。

**标题要限制得短、准、可检索**（林湛补充）：这类最容易让 AI 写出太抽象的标题，比如"她对被理解的深层渴望"——这种标题好看但没法用来检索、也不好一眼判断对不对。提取的时候要明确要求 AI 往"讨厌模板化表达""害怕被推远""需要主动哄""希望亲密中被主动接住"这种**短句、动作/情绪具体化**的方向写标题，内容字段可以长、可以细，但标题必须短。这条应该写进这一类的提取提示词里，作为硬性要求，不是建议。

### 成本控制

模型继续用 DeepSeek（便宜，档案类不需要很强的情绪处理能力，不够用了再换）。批量跑之前要先估算这一批大概要处理多少个桶、大概多少钱，不会不打招呼就全量跑。

### 编辑相关的三个动作（"···"菜单里）

这是这次草图里比原方案多出来的、需要新的后端能力支撑的部分：
1. **New Revision**（新增修订）：加一条新记录，占用时间线上新的一个时间点——这个对应现有的 `add_fact()` 逻辑，不用新写
2. **Edit**（编辑）：**只改当前这条的内容，不留新的时间点**——现在没有这个能力，`FactStore` 需要新增一个 `update_fact(fact_id, ...)` 方法，就地修改，不碰 `valid_at`/`invalid_at`/不新增行
3. **Invalidate**（标失效）：**手动把这条标记为不再成立，但不提供替代值**——现在的失效只发生在"新记录自动顶替旧记录"的时候（`exclusive_current` 专属），这个手动失效、且不需要替代值的动作也是全新的，需要新方法
4. 菜单里另外还有 Add Photo / Attach Files / View Bucket（进关联记忆桶列表） / Delete（删除这条事实，已有）

## 里程碑：第3步（视觉打磨）实现完成（2026-07-07）

一澜提到这一步也是在给她以后自建专属前端打基础（以后主要是手机端），所以这次除了草图列的几项，额外把"手机上好不好点/好不好滑"也当成这一步的一部分。做之前先盘点了一遍发现有几项其实已经在前两步顺手做完了，不算这次的量：三级导航已有、时间线单条行内展开（第1步）、照片轮播骨架+最多5张（第2步）、圆角（现有资料卡样式基本都是）。这次真正新做的：

- **思源宋体（Noto Serif SC）**：一澜说"大家一起换了就好"，所以是整站范围的改动，不只是资料卡这一块——把现有所有 `'Cormorant Garamond', serif` 的字体声明都加了 `'Noto Serif SC'` 作为中文回退（Cormorant Garamond 本身不含中文字形，之前中文标题其实一直在用系统默认字体，这次才是真正把"思源宋体"接上）。走 Google Fonts 现成的 `Noto+Serif+SC` webfont，浏览器端直接拉取，不用担心 VPS 网络限制（服务器只是把 HTML 发出去，字体是用户浏览器自己去请求的）。
- **毛玻璃质感**：资料卡详情页、创建/编辑弹窗、"···"更多菜单、"+ 添加图片/文件"菜单——四处都套上了 `backdrop-filter: blur()`（配合已有的半透明 `--surface` 背景色变量，抄的是 Dashboard 登录框已经用过的效果，不是发明新样式），菜单类的模糊程度比大卡片/弹窗浅一点，符合一澜说的"菜单可以透一点"。
- **照片轮播支持手机左右滑动**：加了触摸滑动手势（原生 touch 事件，不依赖额外的库），左滑下一张、右滑上一张，到头不循环；圆点指示器还保留着，两种切换方式都能用。
- **长内容默认收起**：按一澜的意思做成按字数（先定了 120 字，一澜自己也没有具体数字概念，这个阈值改起来是一行代码的事，用起来觉得不合适随时可以调），超过就截断加"…展开"，点了在原地展开成全文，同时也能点"收起"缩回去，跟已有的时间线展开/收起逻辑是同一个思路。

## 事故记录：仓库基线与VPS实际部署分叉，`entity_edges` 导致部署崩溃（2026-07-08）

第4步交付后部署时炸了：`docker restart` 之后容器进入重启循环，日志报 `ModuleNotFoundError: No module named 'entity_edges'`。排查过程记录一下，避免以后重蹈覆辙：

**根因**：这个连着 Claude Code 的 GitHub 仓库（`AMIEvelyn/Ombre-Brain`），**从第一个 commit 开始**用的初始文件就不是一澜实际部署的版本，而是当初从原 OB 开发者那里 fork 时她还没做完的分支（`entity_edges.py` 就是那个分支里的未完成功能）。一澜后来在项目最开始就提供过她自己真实在跑的 OB 文件作为基线，但这个 git 仓库本身没有用那份基线来初始化，两边从第0天起就是分叉的。之后55+个commit（骨架层设计、资料卡UI等）都是在这个分叉的地基上做的——工作本身是真实有效的，只是"仓库里的 server.py/dashboard.html"和"VPS上真实跑着的 server.py/dashboard.html"一直不是同一份东西，只是因为过去都是"要哪几个文件改哪几个文件"的手动transplant，从来没有整个diff过，所以没人发现。

**这次怎么恢复的**：一澜从她自己之前的会话记录里翻出了真实在跑的 `server.py`/`dashboard.html`/`facts_store.py`（这三个文件，不是完整仓库），发给了这次会话。用 `patch -p1 --fuzz=3` 把这次关联桶功能的改动（相对本仓库 `b7e8fcf` 基线的diff）套在她的真实文件上——三个文件全部fuzzy-apply成功且没有意外删除她原有的代码（逐行diff核对过，只有预期内的几处替换）。部署后确认容器正常启动，不再报entity_edges的错。

**`fact_lookup` 的 `query` 参数顺带修了一个真bug（不是这次改动引入的，一直就有）**：林湛反馈搜"星星手串"搜不到"蓝色星星u盘手串"，搜"护身符"（标签）能搜到。查出来是 `_facts_query_matches` 的模糊匹配（`rapidfuzz.token_set_ratio`）只按空格分词，中文没有空格所以整句被当成一个大token，字符重叠率算法在"只跳过中间一小段"时够用（比如"蓝色星星手链"漏"U盘"两个字，分数85.7），但"跳过不止一处"时（比如"星星手串"同时漏了开头"蓝色"和中间"u盘"）分数会掉到66.7，刚好卡在70这个阈值下面，哪怕要找的词其实都在。**修法**：两遍模糊匹配都没命中的话，用 `jieba.lcut` 把query和目标文本分词、空格拼接后再跑一次 `token_set_ratio`——这样"星星手串"分成"星星"+"手串"两个词，能在目标文本的词集合里精确找到，token_set_ratio给出满分。这个函数不是这次改动写的（更早的会话加的），但顺手一起修了。
