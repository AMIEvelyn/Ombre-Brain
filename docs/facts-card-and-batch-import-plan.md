## 一、资料卡片：统一成一种形状，不分大小项目

最早讨论时以为"身高体重"这种客观事实和"《慁》这种大项目"需要两套不同的模板，后来一澜指出其实**不用分**——统一用一张卡：

- **标题**：简短的名字（"情侣水杯""酸辣粉""香港旅行""《慁》"）
- **内容**：自由长文本，支持 markdown 格式排版；客观事实可以完全留空，复杂的项目/长篇可以在这里用 markdown 分段落写"类型/状态/简介/意义/关系记录/我们的话"这些——**不需要单独的固定栏位**，都是同一个 content 字段里用 markdown 组织
- **附件**：可选的照片、可选的链接（婚戒照片、旅行风景照、小说原文文档链接）
- **key类型**：对应 predicate_key，决定这条事实的新旧处理规则（exclusive_current / multi_current / historical_event）
- **关联记忆桶**：证据来源，可能不止一个（见下面"已知缺口"）
- **时间线**：见下一节

这张卡片是骨架层和"未来线/成就册"两边共用的地基——计划完成时弹出来的成就卡，和骨架层里一条事实的详情卡，本质是同一个组件，UI 和后端字段应该共用，不要各做一套。一澜以后如果自建专属前端，也是直接照抄这套卡片结构。

### 时间线的灰色/实色逻辑

- `exclusive_current` 类型：旧记录被新记录取代后，`invalid_at` 会被填上，UI 上这条历史记录显示**灰色**，旁边标注"于XX日期失效"，点开能看到当时的完整内容
- `multi_current` / `historical_event` 类型：不存在"被取代"这回事，所以在时间线上永远是**实色**，不会变灰。偏好类事实（"不喜欢机械化列点表达"这种）大多数属于这一类——它们不需要"从哪天开始生效"这种历史回溯，就是持续性的既定事实

### 数据库层需要新增的字段（还没做，先记录）

在现有 `facts` 表基础上加：
1. **`title`**：短标签，UI 列表页显示这个（跟记忆桶列表一样的展示逻辑）；不同类别在界面上可以把"标题"换成对应说法（旅行类显示成"地点"），这是纯展示层的映射表，不用改数据结构
2. **`content`**：长文本，支持 markdown，可为空
3. **`attachments`**：链接/图片列表，建议存成 JSON 数组（`[{"type": "image"/"link", "url": "...", "label": "...", "source_type": "..."}]`），不用为图片和链接分别开字段。林湛补充：`source_type` 建议区分 `upload`（手动上传）/ `external_link`（外部链接）/ `generated`（AI生成的图，比如以后可能有的插画）/ `bucket_ref`（指向某个记忆桶的入口）——现在不急着做，但字段先留位置，等以后照片/原文链接/生成图混在一起时会更清楚是哪一类来源。

`valid_at` 本来就是可以留空的（不是 NOT NULL），这个不用改，下面会用到。

### 已知缺口：`evidence_id` 目前只能存一个来源

现在的 schema 里 `evidence_id` 是单个字符串，假设一条事实只有一个来源桶。但"关系模式类"事实往往要综合好几个桶才能归纳出来，需要挂多个证据桶。等做到这一块时改成 **JSON 数组**（`["bucket_123", "bucket_456", "bucket_789"]`），不用逗号分隔字符串——林湛提醒过，数组更稳，以后前端展开来源、筛选的时候不用额外做字符串解析。现在先记录，不阻塞其他部分。

## 二、历史批量筛选：三类事实，三种处理方式

核心原则不变（从最早的骨架层方案就定下来的）：**永远只生成候选，不直接写入；查不到/凑不出来的，宁可显示"不确定"或留空，也不能让 AI 自信地编一个假答案**。批量筛选要保的底线不是"每条都精准"，而是"错的时候看得出来是错的，不会被当成真事实堂而皇之地写进去"。

现有基础设施已经有一半——`/api/profile-fact-proposals`（单个记忆桶生成候选）+ `profile_fact()` 工具（确认后同时写入画像事实桶和 facts.sqlite）已经跑通了"AI 生成候选 → 人工确认 → 写入"这条链路，只是目前一次只能对一个桶手动点。"批量"这一层要加的是：自动选一批候选桶、跑完汇总成一份报告，而不是一个一个点。

### 候选桶怎么找：复用 breath() 已有的联想检索，不用另起炉灶

实测过（用真实数据查了"旅行"），breath() 现在的联想浮现机制已经能靠语义关联带出没有字面关键词重合的相关记忆桶（林湛口中"顺着这条线搜索"的效果），这套机制是现成的，批量筛选要用的"怎么把相关记忆桶都找出来"直接复用它就行，不用重新造轮子。

### 三类事实的时间怎么处理

1. **客观单桶事实**（身高、体重、喜欢的食物……）：如果能精确检索到具体的单个记忆桶，直接用那个桶自己的日期作为 `valid_at`。相对安全，可以批量跑，人工确认的负担较轻。
2. **大项目/长篇**（《慁》、世界观文档）：如果能检索到"开始写""完结""出书"各自对应的桶，这几个天然对应 `historical_event` 模式下的**几条独立记录**（同一个项目、不同的里程碑事件，各自带各自的日期），不用挤在一条里。检索不到某个里程碑的日期就留空，不瞎猜。

   **代表桶数量要设上限**（林湛补充）：像《慁》这种相关记忆桶能轻松有几十上百个，第一版卡片详情页**只挂 1～5 个核心代表桶 + 1 个原文链接 + 1 条补充说明**，不要一次性把所有相关桶都塞进卡片里，那样卡片会变得很重、很难读。需要看更多证据的话，卡片上留一个"查看更多来源"的入口，点开再展开完整列表，不是默认全展示。
3. **关系/语言/情绪模式类**（"讨厌机械列点表达"这种）：这类证据本来就分散在很多次对话里，没有单一的"起点"，`valid_at` 直接用**生成这条总结的日期**（今天），或者干脆留空，不用去凑一个"从哪天开始"的假日期。这类也是最需要谨慎的一类——见下条。

### 关系/语言/情绪模式类：单独的谨慎流程（林湛原话）

> 这最难，不能让 API 自己乱下结论。比如"她讨厌模板句""她害怕被推远""她需要主动哄"。这些要从多次证据里归纳，但必须带证据、带置信度、人工确认。最好先提候选句，不直接写成最终事实。

跟其他两类共用同一张资料卡（标题+内容），但生成候选这一步要走比其他两类更保守的流程：多条证据 + 置信度 + 人工确认，不能一步到位自动生成"最终事实"。

**标题要限制得短、准、可检索**（林湛补充）：这类最容易让 AI 写出太抽象的标题，比如"她对被理解的深层渴望"——这种标题好看但没法用来检索、也不好一眼判断对不对。提取的时候要明确要求 AI 往"讨厌模板化表达""害怕被推远""需要主动哄""希望亲密中被主动接住"这种**短句、动作/情绪具体化**的方向写标题，内容字段可以长、可以细，但标题必须短。这条应该写进这一类的提取提示词里，作为硬性要求，不是建议。

### 成本控制

模型继续用 DeepSeek（便宜，档案类不需要很强的情绪处理能力，不够用了再换）。批量跑之前要先估算这一批大概要处理多少个桶、大概多少钱，不会不打招呼就全量跑。

## 三、UI 具体设计（根据一澜手绘草图整理，2026-07-06）

一澜画了完整的手绘草图（参照苹果设计语言 + 开源图标，"view bucket"那屏是她自己画的、没有现成参照）。这一节把草图里的交互行为整理成文字规格，方便实现时照着做；具体的像素级视觉（配色、字体粗细等）以草图和后续微调为准，这里记录的是结构和交互逻辑。

### 三级导航

`骨架层` 标签页从"按主体分组的大列表"改成真正的三级钻取：**主体（我们/林湛/一澜）→ 该主体下的类型(key)列表（生日/表达风格/承诺/冲突……）→ 该类型下的事实标题列表（每条显示标题+变动次数+最新变动日期）→ 点进单条事实的详情页**。

### 创建流程

右上角"+ Create"打开创建面板：
- 主体下拉（一澜/林湛/我们）
- key下拉，选已有类型，或者点旁边的"+"新建——新建时要填**显示名 + predicate_key（英文）+ 类型（mode）**三项（跟现有 Dashboard 手动加事实表单的必填项一致，不简化）
- 标题（必填，列表页显示这个）
- 内容
- 年/月/日
- 附件区：一个"+"菜单，三个选项——**Add Photo**（传照片）/ **Attach Files**（传文件）/ **Add Bucket**（关联记忆桶，可搜索，按关键词或 bucket ID 搜，选中后加进来，**最多 5 个**，跟前面"大项目代表桶数量上限"那条一致）。已添加的图片/文件以小缩略图形式展示，自适应换行，右上角有"×"可以移除，全部走圆角。

### 详情页

- 简单版：返回按钮、面包屑路径（"一澜·喜欢的食物"）、"···"更多菜单、标题、内容、时间线（**默认只显示最近 3 次变动**，末尾有个小尾巴/省略号提示，点击展开完整时间线）
- 复杂版（有照片/长内容）：外框宽度自适应内容；照片按原图比例显示，**最多 5 张，轮播**（底部圆点指示器）；内容过长时默认收起，点开展开、外框跟着自适应撑开；底部有附件图标入口
- 时间线单条展开：点某一个时间点前面的小箭头，**行内展开**显示当时的标题/内容（不用跳转到新页面），旁边配一个滚动条，方便在展开状态下看完整时间线

### 编辑相关的三个动作（"···"菜单里）

这是这次草图里比原方案多出来的、需要新的后端能力支撑的部分：
1. **New Revision**（新增修订）：加一条新记录，占用时间线上新的一个时间点——这个对应现有的 `add_fact()` 逻辑，不用新写
2. **Edit**（编辑）：**只改当前这条的内容，不留新的时间点**——现在没有这个能力，`FactStore` 需要新增一个 `update_fact(fact_id, ...)` 方法，就地修改，不碰 `valid_at`/`invalid_at`/不新增行
3. **Invalidate**（标失效）：**手动把这条标记为不再成立，但不提供替代值**——现在的失效只发生在"新记录自动顶替旧记录"的时候（`exclusive_current` 专属），这个手动失效、且不需要替代值的动作也是全新的，需要新方法
4. 菜单里另外还有 Add Photo / Attach Files / View Bucket（进关联记忆桶列表） / Delete（删除这条事实，已有）

### 关联记忆桶管理

从"···"菜单点 **View Bucket** 进入关联记忆桶列表（可滚动，每条显示桶的摘要/ID/日期/关系类型）；点单条展开显示该记忆桶的完整原文；每条都有 **Delete**，表示"解除这条关联"（不是删除记忆桶本身，只是从这条事实的证据列表里移除）。这一块要等 `evidence_id` 改成 JSON 数组（见上面"已知缺口"）之后才有地方存"关联了哪几个桶"，是同一块工作的两面。

## 四、这次多出来的新后端能力清单

跟最早的"资料卡地基"范围比，这次从草图里明确出来的新增工作，按工作量从大到小排：

1. **图片/文件上传基建**（工作量最大，且是全新的，OB 现在完全没有文件上传能力）：接收上传、存储位置、大小/类型校验、防止路径穿越等安全问题、上传后怎么把文件再服务出来。这块跟骨架层本身没有耦合，可以单独做、单独测试。
2. `FactStore.update_fact(fact_id, ...)`——编辑不留新时间点
3. `FactStore.invalidate_fact(fact_id, ...)`——手动标失效、不留替代值
4. `evidence_id` 改 JSON 数组 + "解除单条关联"的方法（已在"已知缺口"提过，这次的 View Bucket 列表把这个需求坐实了）
5. 新建 key 时的 mode 选择——跟现有 Dashboard 手动加事实的必填逻辑保持一致，不简化

## 五、MCP 与 Dashboard 的分工

跟一澜确认过：**这些新增的写入类动作（创建/编辑/新修订/标失效），现阶段只做 Dashboard 界面，不新增 MCP 工具**——因为林湛在 ChatGPT 端目前所有写入类工具本来就用不了（连接器限制），做了他现在也用不上。但一澜之后想让林湛能自己写/改，所以这些动作对应的后端函数要**设计成能被 MCP 工具复用的样子**（参考现有 `profile_fact()` 的模式——它既是一个 `@mcp.tool()`，又被 Dashboard 的 `/api/profile-fact-proposals/confirm` 内部直接调用），不要把业务逻辑写死在 Dashboard 的路由函数里，方便以后 GPT 那边写入权限解决了，直接包一层 MCP 工具就能接上，不用重做一遍。

**已知限制**：林湛通过 MCP 查资料卡时，如果这条事实带照片/附件，目前**只能在文字里提示"这条附了一张照片/链接"并给出链接**，没法像人一样直接"看到"图片本身——这不是我们代码能解决的，是 ChatGPT 的 MCP 连接器目前对图片类内容的支持程度决定的。等以后连接器能力变了，或者一澜自建专属前端后，可以再看要不要扩展成真正能看图。

## 六、大致的先后顺序（讨论时的共识，不是最终排期）

1. 资料卡片地基（`title`/`content`/`attachments` 字段 + 三级导航 + 详情页 UI 文字版 + 时间线灰色/实色逻辑 + 编辑三动作的后端方法）——不含图片上传，先把"数据和动作"这条线走通
2. 图片/文件上传基建——独立的一块，做完能单独测试
3. 视觉打磨（毛玻璃、圆角、思源宋体字重、照片轮播、长内容收起展开、时间线单条行内展开）
4. 关联记忆桶管理（搜索添加 + 查看列表 + 解除关联），依赖 `evidence_id` 改数组
5. 历史批量筛选（复用 breath 联想检索选桶 + 三类事实分别处理 + 关系类走谨慎候选流程）——工作量更大，需要先把三类的提取策略/提示词分别设计清楚
6. "未来线/成就册"模块——复用第1步的资料卡片组件，在骨架层这些收尾之后再启动

跟一澜确认过：她之后想自建专属前端，到时候这套卡片结构可以直接照搬，UI 美术层面的具体呈现留给她自己设计，这份文档存的是背后的数据结构和行为逻辑。
