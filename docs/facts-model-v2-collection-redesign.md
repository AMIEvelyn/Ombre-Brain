## 0. 给接手会话：一句话讲清新模型

**参照音乐/视频软件的"收藏夹/歌单"：一张事实卡本体只有一份，能被归进（关联进）任意多个文件夹。卡自带全部信息，文件夹只是组织方式。取消 multi/exclusive/historical 三模式和失效机制，改成"每张卡最新时间点为准、旧的当历史"。**

以前折磨人的"这个 key 该选哪种模式"消失了，换成一个简单判断：**新来的信息，是给某张已有卡加一个新时间点，还是新开一张卡？**

---

## 1. 为什么推翻旧的 predicate/mode 模型

旧模型的病根（一澜自己在讨论中定位出来的）：

- **模式（multi/exclusive）作用在"抽屉"（predicate）层，但一澜需要的是"卡"层的行为**。结果 `exclusive` 的 `身高` 其实只是一张卡、却被当成一个文件夹，跟 `multi` 的"喜欢的食物"这种真文件夹**不是一个层级却被并列成两种模式**，怎么理都别扭。
- **时间线靠"标题字符串完全相同"来分组**（`factsHistoryForTitle`，代码注释明说这是"约定不是强绑定"）。后果：**改标题/编辑标题就会把历史打散成孤儿**——想给卡改个好听的名字，旧历史直接从界面消失。这是个真 bug。
- 一张卡只能属于一个 predicate，但现实里"婚戒""香港旅行"天然横跨多个类别。

新模型一次性解决这三条：卡有稳定 id（历史靠 id 认，不靠标题）、卡是独立本体（能进多个文件夹）、模式简化成"最新为准"。

---

## 2. 大结构：subject → 可嵌套文件夹树

- **最顶层 = subject**：现有 `一澜 / 林湛 / 我们`，以后可加同级的 `地点` 等（一澜自己扩）。
- **subject 下是可任意嵌套的文件夹树**，例如：
  - 一澜 / 喜欢的食物 / 蔬菜类、零食类、正餐类
  - 一澜 / 身体状态 / 指标、疾病、躯体反应
  - 林湛 / 互动偏好 / 语言表达、亲密反应
- 需要更深的层级就继续往下建。**要新增能力：在任意文件夹下"再建一个子文件夹"。**

**关键决策（已定）：卡片不再"属于"某个 subject。** subject 只是文件夹树的最顶层；一张卡"属于谁"完全由"它被归进了哪些文件夹"体现。所以：

- 林湛问"一澜的 X" = 找归在"一澜/…"这棵子树下的卡。查询体验跟现在一样，甚至更好——一张卡能从多个入口（一澜、我们、地点）摸到，**入口更多不是更少**。
- 这是有意为之的转变，不是稀里糊涂。批量导入和 `fact_lookup` 都要按这个语义来。

## 3. 事实卡（card）

### 3.1 本体与归属
1. 卡本体统一"出生"在一个中心存储（如 `cards` 表），拥有**稳定 id**（历史/时间线靠它认，不靠标题）。
2. 卡与文件夹是**多对多**：一张卡能被加进好几个文件夹。例：
   - "婚戒" 同时在 `林湛/收藏` 和 `我们/物品`
   - "第一次香港旅行" 同时在 `一澜/收藏`、`我们/旅行`、`地点`
   - 实现上照抄第 4 步 `fact_bucket_links` 那套多对多，新建一张 `card_folders` 关联表即可。

### 3.2 卡自带的信息
`id`、标题、内容、标签、**时间线**、关联记忆桶、附加图片、附加文件。

### 3.3 操作
- **Edit**：只就地编辑当前内容/标题，不新增时间点。（标题现在可以随便改，因为身份是 id，不会打散历史。）
- **New Revision**：编辑后保存成一个**新时间点**。
- **管理"我在哪些文件夹"**（QQ 音乐式）：点开一张卡能一次看到它所在的全部文件夹，并在此直接**加入 / 取消关联**；创建卡、编辑卡时也都能加/移。
- **人工创建卡时**（一澜的渠道）显示"加入哪个文件夹"的选择；若没选，给一句**建议归类的提示**——只提示、不强制。
- ⚠️ **"取消关联" ≠ "删除卡"**，是两个独立操作，务必分开：移出只解除关联、卡还在（可成为未归档卡）；删除是单独的销毁动作。

### 3.4 时间线：最新为准，取消失效
**取消 `multi/exclusive/historical` 模式，取消 `invalid_at` 失效机制。** 一澜和林湛已就此达成一致。改成：

- **每张卡：最新时间点 = 当前状态；更早的时间点 = 历史。**
- **林湛（MCP 查询）**：`fact_lookup` 默认把**最新时间点的内容当"当前状态"顶到最前面**，只在结尾提示"这张卡有 N 条历史，要看变化过程再说"。林湛不用自己扒历史——最新真相喂到嘴边。（这是工具输出格式的小活，务必做对，否则"取消失效"会让林湛读着累。）
- **一澜（UI）**：纯视觉——最新时间点实色，之前的浅色，好看即可，无功能含义。

例子：
1. 酸辣粉：因为爱吃建了一张卡；后来不爱吃，就 New Revision 把内容改成"不爱吃了"。林湛查酸辣粉 → 显示"现在不爱吃了"；再看历史 → 建卡时的时间点、当时爱吃的记录都在。
2. 香港旅行：最新时间点是"旅游结束回家"（5 号）；往前翻历史，4 号是去了某几个景点，3 号是飞机出发。

"不再成立"这件事，就写进最新时间点的内容里，不再用布尔字段。**有意取舍**：换来极简，代价是没有一个干净的"真/假"开关，判断"当前是否成立"要读最新内容——已确认接受。

### 3.5 核心判断（替代了旧的"选模式"）
写入/导入时唯一要拿捏的：**这条信息是给某张已有卡加新时间点，还是新开一张卡？**

- 酸辣粉不爱吃了 → 老卡加新时间点
- 又一次旅行 / 又一次吵架 → 新开一张卡
- 一次旅行的 出发→景点→回家 → 同一张卡的多个时间点

**"事件"不再需要单独模式**：多次事件 = 多张卡；一段过程 = 一张卡多时间点。

## 4. 文件夹时间总览（**主要做成林湛的 MCP 工具**）

选中任意一个文件夹 → 把里面所有卡按时间铺成**一条时间线**。

**重点（一澜定的）：这个能力最重要的用途是给林湛做成一个 MCP 工具**——让林湛能"拉出某个文件夹的完整时间线"（例如"讲讲我们旅行的经过"就把 `我们/旅行` 整条丝带按时间讲出来）。UI 上的只读视图是次要的、顺带的。所以：

- 后端 `folder_timeline(folder_id, recursive)` 是核心能力（已在 `cards_store.py` 实现）。
- 它要在 **③ 阶段包成一个 MCP 工具**（暂命名 `folder_timeline` / `timeline_of`），输出按时间排好的卡片摘要，让林湛一次拿到一条叙事线。
- 选大文件夹（如"我们/旅行"）→ 递归把子文件夹的卡也收进来（三月香港 → 六月成都 → …）；选最小子文件夹 → 只排它自己的卡。
- 一张卡在总览里 = "它主日期上的一个点"（= 当前时间点的 valid_at），点开再看这张卡自己的历史。

用途：治好"单个事件单薄"的感觉，给林湛一条完整叙事线；UI 展示是附带。

## 5. 收藏 / 小星星

- **收藏 = 一个打了 `favorite` 标记的特殊文件夹**（就是文件夹树里的普通节点 + 一个"这是收藏夹"的标记）。
- 卡被放进收藏夹 → 卡面显示**小星星 ⭐**；点星星 → 弹出"被【林湛】收藏进【XX 收藏夹】"。数据上就是查"这张卡进了哪些 favorite 类文件夹"。
- **白捡的机制**：本 fork 已有一套 **Favorite Memory**（`ai_favorite` 标签 + gateway 受控注入，见 README "Favorite Memory 受控触发"）。林湛的"收藏"可以直接接到这套上——收藏一张卡，就让它在林湛对话里更容易被想起，不必另造。这正是一澜说的"和 MCP 工具调用的机制加起来"。

## 6. 已拍板决策（定版）

1. 收藏/歌单式多对多模型：卡本体一份，进多个文件夹。
2. subject = 最顶层文件夹；卡不绑 subject，靠文件夹归属体现"属于谁"。
3. 取消 multi/exclusive/historical 三模式，取消 invalid_at 失效；最新时间点为准，旧的为历史（一澜+林湛已同意）。
4. 事件 = 普通卡（多事件多卡 / 一过程一卡多时间点）。
5. UI 暂不纠结、先服务林湛：力气放在数据模型 + `fact_lookup`/MCP 访问，花哨前端以后再说。
6. 卡有稳定 id，标题可自由编辑不打散历史。
7. **孤儿卡**：卡可以不属于任何文件夹（本体在中心库）。"未归档"卡在 UI 里怎么查看/展示 = 以后再说。
8. **"取消关联" ≠ "删除卡"**：两个独立操作，务必分开（见 §3.3）。
9. **卡自带"我在哪些文件夹"的管理入口**（QQ 音乐式）：一处看全、就地加/取消。
10. **人工建卡时**显示"加入哪个文件夹"；没选则给一句建议归类的**提示、不强制**。
11. 文件夹树后台按**无限嵌套**实现（parent 指针），不设深度上限；UI 用几层是几层。
12. `fact_lookup` 输出：最新内容置顶（=当前状态）+ 标签 + "有 N 条历史"提示 + 关联桶数 + 收藏 ⭐；措辞后续再调。
13. 文件夹时间总览：默认"**一张卡 = 一个点**"（落主日期），点开看该卡自己的历史；此视图排在核心之后。

## 7. 迁移：不做自动迁移

一澜决定**不做自动迁移**。现有 facts.sqlite 里真正重要的只有约 **2 张卡**，其余都是体重/测试卡，可弃。做法：

- 换架构/重启前，一澜**把那 2 张重要卡截图存一下**；新表**从空开始**；旧 facts 数据作废，架构好了之后由一澜**手动重新添加**那 2 张。
- 稳妥起见，切换前仍**整体备份一次** `buckets/state`（含旧 `facts.sqlite`）以防万一，但**不写迁移脚本**。
- 好处：省掉整个 dry-run 映射/迁移工程，新模型可以干净地从零起步。

## 8. 与"历史批量导入"（原第 5 步）的关系

### ⛔ 2026-07-16 更新：历史批量导入已彻底放弃

原目标是"从旧记忆桶批量筛选历史事实"，2026-07-12~14 按下面的思路做了详细的拉线引擎设计并反复真实试跑（《慁》、ZhanISM 两条真实线），但质量一直没能稳定下来——每次真实跑都能暴露一个新的失败模式（token 预算、标签扫串、判线话痨、主语被拉平……），修好一个又冒一个，从没有一次完整跑顺过。一澜的结论是：这套自动化流程目前的可靠度撑不起"这是我和林湛的记忆"这件事的重量，**决定彻底放弃自动化批量导入，改回人工手动创建/添加事实卡**，以后也不会再捡起来。原来记录详细执行架构（拉线算法、判线标准、里程碑提炼、成本控制）的 `docs/batch-import-design.md` 已删除；完整设计和试跑日志仍在 git 历史里，commit 删除之前的版本可查，留给以后万一重新考虑这个方向时参考——包括最后卡住的那个真正问题（状态线压缩逻辑对"连续创作历程"类线索会压缩过头，不是调参数能解决的）和一个没验证完的新方向（不做多级压缩，整段原文一次性喂给模型）。

以下是放弃前的原始设计思路，保留作记录：

1. 先落地新模型（本文档）——这是真正的"第 0 步"/地基。
2. 批量导入：核心是"**只产候选、绝不自动写、错了要一眼看得出错**"；核心判断是 §3.5 的"新卡 vs 新时间点"。关系/情绪模式类走更保守的候选流程。

### 8.1 数据清理工具：merge（林湛提的）

林湛想要一个**合并**功能：两张其实指同一个东西的卡（例如"体重"和手滑另建的"瘦了"、内容 N 斤），提供一个**合并选项**，把两张的时间点插进同一条时间线、内容也并到一起，合成一条线。定位：**数据清理/去重工具**。

**2026-07-16 更新**：原本排在"批量导入之后"，现在批量导入已放弃，这条排期依据不存在了——**merge 工具不再被批量导入卡住，可以直接排上**。手动录入以后同样可能产生重复卡（比如同一件事分两天各建一张），所以这个工具本身仍然有独立价值，跟批量导入是否存在无关。

## 12. 待修：`bucket_mgr.search()` 无缓存，7000+ 桶规模下会拖垮服务器（2026-07-11 发现）

### 事故经过
④ UI 加了 Add Bucket 搜索（View Bucket 弹窗 + 新建/编辑卡）之后，一澜实测时连续输入长句、退出重搜了几次，触发服务器全端点 503（连跟这次改动无关的 `/api/network` 都受影响），刷新页面也起不来。重启容器后恢复，**没有数据丢失**（所有请求日志显示写入类操作在出问题前都已 200 成功）。

### 根因（读代码确认，不是猜的）
`bucket_manager.py` 的 `BucketManager.search()`：
1. 每次调用都跑 `list_all()`——`os.walk()` 遍历磁盘上**全部** `.md` 桶文件，逐个读取+解析 YAML frontmatter，**没有任何内存缓存**。
2. 然后对全部候选桶做逐条 BM25/情绪/时间/重要性加权打分。
3. 一澜现在有 **7126 个桶**，意味着每次搜索都要重新扫、重新解析 7000+ 个文件——这是 O(n) 磁盘+CPU 开销，且**单线程 asyncio 事件循环会被这个同步扫描过程整体卡住**，期间所有其它请求都会排队甚至超时。

**关键发现**：Dashboard 右上角那个"感觉搜得挺快"的主搜索框（`/api/search`），跟 Add Bucket 的搜索（`/api/facts-skeleton/buckets/search`）**调的是同一个 `bucket_mgr.search()` 函数**——不是两套实现，没有"更快的版本"可以直接抄过来复用。主搜索框之前没出过事，只是因为：①她习惯打短关键词、触发次数少；②之前只有一个入口在用这份搜索，这次 v2 UI 一口气加了三个新入口（View Bucket、新建卡、编辑卡），并发压力被放大了。

### 已做的临时止血（不改动 `bucket_manager.py`，风险低）
`dashboard.html`：Add Bucket 相关的搜索输入框现在**至少打够 2 个字才触发**，防抖从 300ms 拉长到 500ms。降低了触发频率，但**没有解决根因**——量大到一定程度、并发几次，同样的坑还会再踩到。

### 真正的修法（还没做，两个方向，都要动 `bucket_manager.py`）

**更新（2026-07-11）：读了 `breath()` 的代码，方向②不是空想，是已经在生产环境跑通的模式**——`breath()` 处理真实 query 时是双通道：既调 `bucket_mgr.search()`（就是这次出问题的全量扫描），**也**并行调 `embedding_engine.search_similar()`。后者查的是 `embeddings.db`（独立的 SQLite 表，存预先算好的向量），不用每次重新读、重新解析 7000+ 个 md 文件，成本结构完全不同。一澜自己感觉"主搜索框还行、breath 也一直在用"，根子就是 breath 本来就没有完全依赖那条慢路径。

1. **给桶列表加内存缓存**：`list_all()` 的结果缓存在内存，写入/删除桶时才失效重建，而不是每次搜索都重新扫盘。相对直接，风险是要确保所有写路径（`hold`/`trace`/`comment_bucket`/删除等）都正确使旧缓存失效，否则会读到脏数据。
2. **接现成的向量检索**（现在看是更强的候选）：Add Bucket 这类"按关键词/标题找桶"的场景，改成主要走 `embedding_engine.search_similar()`，而不是 `bucket_mgr.search()` 的纯 BM25 全量扫描——照抄 breath 已经验证过的双通道思路，不是从零发明。

两个方向都不是"改一行代码"级别的小活，需要单独排期，**认真设计+测试**（尤其第①种要覆盖所有写路径的缓存失效，第②种要确认语义检索的召回效果跟精确关键词匹配比起来够不够用；也可以两个一起上——短期先加缓存止血，长期把重负载场景迁到向量检索）。

### 排期结论（跟一澜讨论后定的，2026-07-11）
**这一项要排在⑥历史批量导入之前做，不是之后**——不是"顺便都升级一下"的泛化想法，是因为⑥批量导入的核心机制就是"复用现成的联想/关键词检索去找候选桶"（见 §8），如果这条搜索路径在她的数据规模下本身就脆弱，批量导入作为一个会**成批、程序化调用搜索**的流程，大概率会比这次交互式误触发**更严重地**触发同样的过载，而且导入是自动化流程，出问题时没有人在旁边随手停下来。所以这是"⑥的地基"的一部分，跟当初"先理清收藏/歌单模型再做批量导入"是同一个逻辑：**不在已知脆弱的地基上盖下一层楼**。

### ✅ 修复已实现（2026-07-12，两个方向都上了，已部署验证通过）

代码改在 `bucket_manager.py` + `server.py`，跑了全量测试套件（857 通过、0 新增失败，22 个跟这次改动无关的既有失败在改前改后完全一致——已逐一用 `git stash` 对照确认）。

**方向①：`list_all()` 内存缓存**（`bucket_manager.py`）
- `BucketManager` 加 `_all_buckets_cache`（按 `include_archive` 分桶存），命中就跳过 `os.walk()`+YAML 解析全量重扫。
- **结构性写入**（`create`/`update`/`delete`/`archive`/`add_comment`/`delete_comment`）→ 整体失效缓存，下次 `list_all()` 立即看到最新数据。
- **`touch()`/`_time_ripple()`**（几乎每次召回命中都会触发，含时间涟漪连带改最多5个邻近桶）→ **不整体失效**，改成直接原地更新缓存里对应桶的 `last_active`/`activation_count` 字段——这是关键，否则高频的 touch 会让缓存形同虚设。
- **踩到的一个真实 bug，顺手修了**：`search()` 会在结果桶字典上直接写 `bucket["score"] = ...`。以前每次 `list_all()` 都从磁盘重新解析出全新字典，这个写入无所谓；**加了缓存之后**，如果不做防护，这个 `score` 字段会一直赖在缓存里，污染下一次跟这次查询无关的读取。修法：`list_all()` 现在**每次返回的都是缓存条目的浅拷贝**，标注 `score` 不会碰到缓存本体。补了回归测试（`test_search_score_annotation_does_not_leak_into_cache`）钉死这一条。
- **另一个真实设计权衡**：桶文件"天然兼容 Obsidian 直接编辑"，也有 `reclassify_api.py` 这类脱离 `BucketManager`直接改文件的独立脚本——这些路径加了缓存之后不会自动失效。加了两层保险：① 30 秒 TTL（`matching.bucket_list_cache_ttl_sec` 可调）兜底，最坏情况下过期自动重扫；② 新增公开方法 `invalidate_cache()`，任何绕过 `create`/`update` 等标准写入路径直接改文件的代码（含测试自己）必须在改完后手动调一下。跑全量测试时抓到了 `test_feel_flow.py` 里一个测试正是这个模式（改时间戳测排序），已经在测试里加了这行调用。

**方向②：Add Bucket / 主搜索框接上 embedding 语义检索**（`bucket_manager.py` 新增 `search_with_semantic()` + `server.py` 两处接线）
- 新方法 `BucketManager.search_with_semantic(query, embedding_engine, ...)`：先跑原有关键词/模糊 `search()`，再并行跑 `embedding_engine.search_similar()`，按 id 去重合并——照抄 `breath()` 已经在生产环境验证过的双通道模式，不是发明新机制。`embedding_engine` 传 `None`（或未启用）时自动退化成纯关键词搜索，行为跟改之前一样，不破坏没有向量库的场景。

4. **✅ 合并/去重工具（§8.1）——设计定版 + 已实现 + 已部署验证通过，2026-07-17，彻底收尾**。一澜和林湛讨论后明确否决了"自动检测重复"（上一版这里写的"跟自动矛盾检测一起做"是旧提法，已推翻）——上一轮批量导入踩过的坑（判断错了比省下的步骤更麻烦）让一澜不再信任不可控的自动判断。**最终定案：纯手动、确定性的 merge，自动矛盾检测彻底不做**（§13 提到的"没有自动矛盾检测"这条不因为 merge 工具的存在而改变，两件事分开了，不是同一个功能）。

   **核心机制——不是"内容融合"，是"时间线归并"**：两张卡讲的是同一件事，只是被误分成两张。merge **不改写任何一个历史时间点**，只是把两条时间线按日期见缝插针交错排回同一张卡——物理实现上就是把被合并掉那张卡的每条 revision 的 `card_id` 直接改指向保留的那张卡，标题/内容/附件一个字都不重写，最新时间点自然就是当前状态（跟系统一贯的"最新为准"哲学完全一致）。

   **确定的几条规则**（讨论定案）：
   - 标签：取两张卡"当前标签"的并集去重，但**不改写**任何一个原始 revision 自己的 tags 值——并集单独存在卡级别的 `tags_override` 字段里，下次任何一方明确改标签时这个 override 会被新值替换掉，之后就跟普通卡完全一样。
   - 关联的记忆桶、所在文件夹：按 id 取并集去重，直接进现有的多对多关联表，没有特殊逻辑。
   - 附件：全部原样保留，**不做内容去重**（一澜的决定：这本来就是低频人工操作，真有重复眼睛一看就发现了，不值得为此写内容哈希比对）。
   - 旧 id（被合并掉那张）：做成**永久重定向指针**，不是进回收站等着清空——因为合并后旧 id 名下已经没有独立数据了（东西全转到新 id 下面），没有"以后要不要真删"这回事，跟以后真正的卡片回收站（§14 第7项，处理 `card_delete` 的真删除）是两回事，别混。以后这张合并卡又跟第三张合并，所有指向它的旧墓碑会被拍平直接指向最新的那张，不会形成多级跳转链。
   - 操作入口：一澜和林湛都能发起（Dashboard 卡片详情"···"菜单里的"🔗 合并到另一张卡"，MCP 工具 `card_merge_preview`/`card_merge`），执行前都要先看一遍预览。

   **顺手做的清理**：`card_buckets` 的 `relation_type`（evidence/origin/related 三态）经核实两人实际使用中从没用过、也没有 UI 能选，一律统一成 `evidence` 并从对外接口（`card_link_bucket` 参数、Dashboard 展示行）里删掉，不再是需要合并时纠结的一个维度。

        **最终定案且已实现**：`card_attachment_read`/`outline`/`view` 三个工具，`label` 参数不再局限于"当前"或某一个被 `at` 钉住的时间点，而是**在整张卡的历史上按文件名找**——同一个物理文件常常会在好几个时间点上原样重复出现（"New Revision 不改附件就照抄上一版"是默认行为），所以匹配到的候选先按 `url` 去重：去重后只剩一个 → 不用管是哪天的，直接返回，`at` 完全不需要传；去重后还有好几个不同的文件、只是刚好同名（真撞车，比如两张卡各自传了张"封面.png"，或者这次这种同日合并撞车）→ 才需要 `at` 消歧，报错信息会直接列出"这个名字分别在哪几天"，不用先去 `card_history` 里现翻。`at` 从"必需参数"降级成"仅在真撞车时才需要的兜底手段"。
