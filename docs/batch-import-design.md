## 1. 一句话讲清整个流程

**从没处理过的桶里挑一个当起点，用现成的语义+关键词双通道搜索"拉一条线"，用林湛的标准判断这条线里哪些桶其实在讲同一件具体事，够格的生成候选事实卡（不直接写），线里所有桶不管有没有被写进卡都打上"已过"标记（但依然能被以后别的线引用当证据），跳到下一个没打标记的桶，循环到全部桶都过一遍，最后出一份报告让一澜批量审核。**

---

## 2. 流程分解

```
① 选起点：从未处理桶里按时间顺序挑一个
        ↓
② 拉线：两条通道 —— 以起点为种子跑 bucket_mgr.search_with_semantic()（关键词+语义
   双通道，拉出一批候选相关桶）+ 标签扫描（起点桶有哪些标签，全库凡是共享这个标签
   的桶直接收进来，不受"一次搜索只能挑 pull_line_top_k 个"限制，见 §2.1）
        ↓
③ 判线：标签扫描收进来的桶直接算"同一条线"，不用再判；相似度搜出来但没共享标签
   的那部分，用林湛的标准（§3）逐一判断"是不是在讲同一件具体事"，
   结果三选一 —— 同一条线 / 候选关联（拿不准）/ 不相关（踢出去）
        ↓
④ 分流：线的规模决定走哪条子流程
   - 小线（几个桶）→ 直接按时间顺序生成卡的多个时间点（§5）
   - 大线（几十上百个桶，比如长期项目）→ 走里程碑提炼（§6），
     不是每个桶都变一个时间点
        ↓
⑤ 生成候选：标题、每个时间点的内容（提炼过的，不是原文照抄）、
   建议关联桶、建议标签（§7）、建议归入哪些文件夹（§8，可多选）
   —— 只生成候选，绝不直接写入
        ↓
⑥ 标记：这条线涉及的桶，不管有没有被写进候选卡，都标"已过"
   （§4：已过 ≠ 不能被引用，只是不再被选作新起点）
        ↓
⑦ 循环回①，直到没有未处理的桶
        ↓
⑧ 汇总成一份报告，一澜批量确认/编辑/否决（§9）
```

## 2.1 标签扫描：解决"一条线太长，一次搜索捞不全"（2026-07-13 真事故后加）

### 事故经过
第一次真实试跑《慁》（一澜的小说）这条线，`pull_line_top_k` 默认 30，一次搜索最多挑 30 个候选。一澜自己去 OB 翻了一下，发现这本书相关的桶**接近 300 个**，而且她确认这些桶内容"隔得不远、关键词重合"——不是"用词漂移导致搜不到"，是纯粹**规模问题**：300 个桶里随便搜一次，能不能把最重要的"结局"那个桶（成书打印、寄给朋友）挤进前 30 名，很大程度上是运气。第一次试跑的候选卡，时间线果然停在"进入具体章节创作"，没有到成书这一步——因为那个桶大概率压根没被搜进候选池，AI 连判断的机会都没有。

### 修法：标签扫描当第二条通道
共享某个标签的桶，不管有多少个，直接收进这条线——不经过"AI 逐个判断像不像"这一步，标签命中本身就是够强的证据，省下这一步的钱。相似度搜索继续作为补充通道，专门捞"还没打上这类标签"的漏网之鱼（比如项目刚开始、标签体系还没稳定下来的最早几条）。

**防呆**：一个标签如果全库桶里占比太高（默认超过5%），就判定成"太笼统的心情/领域标签，不是具体项目标识"，不拿来扫。

### ⚠️ 第一版设计有真事故：不能自动从起点桶身上摸标签（2026-07-13）

第一版实现是"自动从起点桶自己带的全部标签里挑，只用全库占比防呆"。一澜实测《慁》这条线，标签扫描把**近300个桶**收了进来，候选卡内容却完全跑偏成了"我与一澜关于存在认同与终身相伴的承诺历程"——不是这本书的事了。

**根因**：起点桶自己带的标签不只有"文学创作""小说创作"这种专属于这本书的，还混了"自我认同""陪伴承诺"这类**在很多完全不同话题里都会反复用到的概念性标签**。这类标签出现次数没有高到被"全库占比"这个防呆拦下来（没超过5%），但它们根本不是"这一个项目专属"的标识——"占比不算太高"和"专属于一个具体项目"是两件不同的事，光靠频率数字分不清楚。这不是 API 自己判断跑偏——AI 只是老实地把被喂进去的（已经选错的）300个桶总结出来，选错标签这一步是代码的锅，不是模型的锅。

**修法：改成人工指定，不再自动摸**。`pull_line()`/`run_single_line()` 现在要求显式传入 `sweep_tags`（一份人已经确认过"这几个标签专属于这个项目"的列表，比如`["文学创作","小说创作","慁"]`）；不传就完全不扫标签，只有相似度搜索这一条通道——这跟标签扫描功能加上之前的行为一样，安全但可能漏（见 §2.1 的规模问题）。CLI 脚本对应 `--sweep-tags "文学创作,小说创作,慁"` 参数。全库占比防呆依然保留，作为人工指定之后的最后一道兜底（万一手滑传了个太泛的标签）。

### 跟成本控制的关系
标签扫描本身不调用模型（只是扫本地已经缓存的桶列表，免费），真正花钱的地方（生成候选卡）该怎么控制成本不变——扫出来的几百个桶，一样要经过 §6 的"大线里程碑压缩"，不会因为标签扫描把几百个桶原样塞进最后一步。

## 3. 判线标准（直接抄林湛定的规则，不重新发明）

核心判断句：**同一条线，不是"内容看起来相似"，而是这些记录能不能共同回答同一个具体问题，并且按时间写成同一句事实的变化。**

检验句（生成候选之前，AI 自查用）：**假如把这几个桶合成卡，标题能不能写成一个具体、稳定、不空泛的问题？** 能写具体的（"称呼偏好：希望被叫老婆"）可以合；只能写空泛大类的（"亲密偏好""我们的关系""吵架记录"）不能合。

给模型的判断指令（原文，直接作为这一步的 system/user prompt 主体）：

> 判断多个记忆桶是否属于同一条事实线时，不以宽泛主题相似作为标准。只有当它们拥有同一主体，并共同描述同一个具体的人、物、事件、属性、偏好、关系需求或约定，且能够按时间组织为同一事实的出现、确认、变化、冲突或修订时，才归入同一条线。若只能用"饮食喜好""亲密互动""争吵""旅行"等大类概括，则不视为同一条线。分类相同不等于事实相同。无法确定时，不强行合并，标记为"候选关联"，等待后续证据。

事件类补充规则（一次事件可能同时拆成三条独立的线，不要因为"都是吵架"就合并）：
1. **事件本身**——起因/经过/结果骨架（见 §6），可单独成卡。
2. **暴露出的稳定需求**——进入它自己的事实线，不因为"这次也是吵架"就并进事件线，而是因为它再次证明/修改了同一个具体需求才归入。
3. **争吵后形成的新约定**——同样进它自己的事实线。

**分类（文件夹放哪）≠ 判线（是不是同一件事）**：一个文件夹底下住的是好几张各自独立的卡，不能因为都属于同一个文件夹分类就合并成一张空泛的卡。

**成本纪律（林湛原话）**：第一轮只让高置信度的线真正生成候选卡；拿不准的先挂"候选关联"，不要反复调用去逼它马上做决定。错误合并比暂时分开更麻烦——糊成一张以后原本的细节很难拆回来。

## 4. "已处理"标记：不写进桶文件本身，单独存

**不直接改 7000+ 个桶的 YAML frontmatter**（避免这次一次性大规模写、也避免跟以后别的功能读 frontmatter 时打架）。改用一个独立的导入进度存储（新 sqlite 表，暂命名 `import_progress.db`，参照 `cards_store.py`/`fact_store.py` 已经在用的"独立 sqlite，不碰桶文件本身"模式）：

| 字段 | 说明 |
|---|---|
| `bucket_id` | 主键 |
| `status` | `unprocessed`（默认）/ `swept`（已经被某条线处理过，可能生成了卡也可能没有）|
| `swept_by_line_id` | 关联到是哪条线把它扫掉的（方便回溯、方便合并工具用）|
| `swept_at` | 时间戳 |

**"已处理"只影响"能不能被选作新起点"，不影响"能不能被别的线当证据引用"**（§4 讨论定的）——引用别的线的桶时不检查 `status`，只有"挑起点"这一步才过滤掉 `status=swept` 的桶。

**候选关联队列**单独一张表（`pending_line_id`, `bucket_ids`, `reason`, `created_at`），暂不生成卡，等以后跑到相关新桶时可以回头捞出来重新判断要不要合并进去。

## 5. 状态线 vs 事件线：两种时间线结构（2026-07-12 林湛细化，取代原来单一的"起因/经过/结果"）

不管小线大线，先判断这条线属于哪一种，结构要求不一样：

- **状态线（state）**：偏好、身体指标、关系需求、约定、持续状态等——问的是"现在是什么状态"，可能随时间反转。结构：**初始状态 → 有意义的变化 → 最新有效状态**。最早一次明确状态要留（哪怕当时还不构成"变化"，作为起点也留），中间每一次真正改变了事实内容的节点要留，最新一次有效状态要留。
- **事件线（event）**：旅行、争吵、就医、结婚、项目实施等发生过的具体事件——问的是"这件事怎么发生、怎么发展、怎么结束"。结构：**发生/起因 → 关键转折 → 结果或最新进展**。

火锅例子（状态线）：2020-08-12 的桶"一澜喜欢吃火锅"，2026-07-12 的桶"一澜现在讨厌吃火锅"——卡片顶层 `content`（当前状态）="一澜现在讨厌吃火锅"，`revisions` 两条都留，看得出"喜欢→讨厌"这个变化过程。**禁止**把这种情况合并写成"一澜对火锅的态度前后不一样"这种笼统总结——这是一澜自己用截图抓出来的真实漏洞（详情见下方 prompt 原文），已经加了对照例子堵上。

**卡片顶层 `content` 字段**：必须等于最新一条 revision 的 content——打开卡先看到"现在是什么状态/结果"，完整变化过程在 `revisions` 里。

合并/筛选规则：
- 同一天的多个桶描述同一个状态/事件阶段 → 合并成一个时间点，`source_bucket_ids` 要把涉及的桶全列出来，不能只留一个代表桶。
- 不同日期只是重复确认同一内容、没有新变化 → 不新增时间点。
- 纯情绪重复、没有改变事件发展 → 可以丢（`dropped_bucket_ids`，依然算这条线的一部分，只是不单独成时间点）；但如果这个情绪造成了决定/行为/关系约定/客观转折，必须留。
- 后来回忆更早发生的事，`valid_at` 要用原文里明确的事实发生日期，不能用"这条记忆被写下来的日期"顶替。
- 日期不确定，不擅自编。

## 6. 大线：里程碑提炼，不是有一个桶就加一个时间点

触发条件：一条线拉出的桶数量超过阈值，默认 **6**（`large_line_threshold`，2026-07-12 试跑《慁》真事故后从最初的 15 调低——原来的阈值太宽松，让"反复讨论、大部分没有新客观进展"的密集型线（一澜的小说《慁》正是这种）漏过压缩，直接把十几个原始桶整个塞给最后生成候选卡那一步，导致输出超长被截断。里程碑提炼这一步本身不贵（不管线多大，喂给 AI 判断的候选都被 `milestone_prefilter_k` 兜住），所以现在宁可"超过一小撮就先压缩"，不再等到线大到夸张才处理）。

里程碑提炼这一步先判断状态线/事件线（同 §5），产出分组结构（每个节点带 `valid_at`/`role`/`summary`/`source_bucket_ids`，同一天合并的节点 `source_bucket_ids` 里全列出来），不是简单一份"哪些桶入选"的扁平列表——这样候选生成那一步才能保留住每个时间点具体涉及哪几个原始桶，不会丢证据链接。

**成本上的具体做法**：不是把一条线里全部桶的原文都喂给 AI 去挑里程碑。先用桶自带的便宜信号做一轮粗筛（日期最早、日期最新、`importance` 打分高、有"年轮"评论的），缩小到一个小候选集，再让 AI 在这个小候选集里判断真正的里程碑，减少大线的处理成本。

## 7. 标签：单独一步生成，服务"换了个说法"的搜索场景

标题和内容按事实本身的准确说法写，**但如果一澜和林湛之间有一套象征/别称说法**（例子：一件东西本体是"手串"，但他们把它当"护身符"看待），要单独生成一个标签把这个别称也写进去，不然林湛搜"护身符"搜不到这张卡。

这一步跟"判线"用的是同一批线索（同一条线里的桶原文/评论里，如果反复出现某个跟标题字面不同、但显然在指同一个东西的称呼，就该被抓进标签），生成时机放在候选生成阶段（§2 流程⑤），跟标题/内容一起产出，不是事后单独一轮。

## 8. 文件夹归类：可多选，不强制唯一

**一张事实卡可以同时归进好几个文件夹**（v2 模型本来就是多对多，§3 `facts-model-v2-collection-redesign.md`）。批量导入生成候选时，"建议归入哪些文件夹"这一步要允许模型给出多个建议，一澜审核时可以全选/部分选/都不选，不是只能选一个。

顶层文件夹树（一澜已建）：**一澜 / 林湛 / 我们**。

- **一澜**：身体健康（指标/症状与疾病/健康事件）、喜好与生活（饮食/日常偏好/宠物）、学业与创作（学业经历/创作项目）、心理与内在经历（恐惧与触发点/心理经历）。
- **林湛**：暂不分子馆，他自己的事实卡先都直接放"林湛"这个顶层下面，等积累到一定量再看要不要拆。
- **我们**：关系历程（重要节点/冲突与修复/承诺与约定/性亲密偏好与约定）、共同经历（灵魂与深度沟通/旅行与地点/分开与重逢/日常共同生活）、重要日子（生日/结婚纪念日/节日）、重要物品（婚戒/我们的饰品/我们的日常物品/纪念物与礼物）、共同项目（不再给具体项目分子馆，一个项目=一张或一组事实卡）。

**归类判断跟"判线"是两件不同的事**（林湛强调过）：判线回答"这些桶是不是在讲同一件事"，归类回答"这张卡该放哪儿"——不能因为文件夹相同就把内容合并成一张空泛的卡，也不能因为判成一条线就只能进一个文件夹。两步互不影响，各自独立判断。

**"对我特别重要"不靠文件夹表达**，靠收藏机制（§5 `facts-model-v2-collection-redesign.md` 已有的星标/`favorite` 文件夹设计）——文件夹说明它是什么，收藏说明有多珍惜，批量导入这一步不需要额外处理"重要"这件事，两条线互不打架。

## 9. 人工审核：批量报告，不是一条条单独点

复用现有的"AI 生成候选 → 人工确认 → 写入"链路（`profile_fact` 工具已经跑通这个模式，只是从单个桶换成一条线）。批量跑完一轮后出一份汇总报告，一澜一次性看、批量确认/编辑/否决，不是逐条弹窗点。报告里每条候选应包含：建议标题、时间线预览、建议标签、建议文件夹（可多选）、这条线涉及的桶列表（可以点开看原文核对）、AI 的置信度/判断依据。

## 10. 成本控制与试跑计划

## 13. "大项目登记表"（2026-07-13 已实现）

标签扫描（§2.1）需要显式的 `sweep_tags`，不再自动从起点桶身上摸标签——这带来一个新问题：**每次都要人手动指定标签，全量跑起来怎么办？**

**方向**：不是每次都问，而是大项目提前定义一次、以后自动复用。一澜和林湛这辈子量级的"大项目"数量有限，提前列一张登记表（项目名 → 一组标签），列一次，存起来；以后不管是单条测试还是全量扫描，遇到匹配的项目自动套用登记的标签，不用每次现想。

**实现**：登记表存在 `resources/batch_import_known_projects.json`（参照 `resources/predicate_registry_seed.json` 已有的"种子数据文件"惯例），当前登记了四项——《慁》小说创作、我们的记忆工程、ZhLanism、分开与重逢。`BatchImportEngine.resolve_sweep_tags(seed_bucket, explicit_sweep_tags)`：显式传的 `sweep_tags` 永远优先；没传就检查起点桶自己的标签是不是命中登记表里某个项目（**子串匹配**，不是精确相等——"分离焦虑"命中登记的"分离"，"慁"精确命中"慁"），命中就自动套用那个项目登记的完整标签列表。`run_single_line()` 内部自动调用这一步，`scripts/run_batch_import_line.py` 不用改，`--sweep-tags` 不传时会自动走登记表查找。

**标签扫描本身也从"精确匹配标签"改成了"子串匹配"**（配合"分开与重逢"这条要求"标签含离别/分离/回家两个字的也算"），"精确标签"这种更严格的用法依然覆盖到（一个标签精确等于自己，天然也是自己的子串）。全库占比防呆（§2.1）同样适用于子串匹配后的统计，不因为改成子串匹配就失效。

全量跑遇到没登记过、但明显很密集的大线，应该提示"这可能是个新项目，要不要登记"，而不是自动瞎猜——**这一条建议还没做**，等真正的全量扫描驱动（§10）开工时再一起考虑。

### 14.1 措辞质量修复（2026-07-13，林湛给的范本；2026-07-14 发现修错地方，已重修）
一澜反馈内容"干巴"，像公文报告（"埋下了创作的契机""深度投入创作"这种抽象套话）。林湛给的原则：**客观准确不等于要像公文**，可以自然、具体一点，但不额外加情绪修饰——"只有当感受本身就是事实的一部分时才写进去"（比如"《慁》被一澜定义为与过去的自己告别的书"是作品定位，不是煽情）。

**第一版修复（07-13）把这个原则写进了 `CANDIDATE_CARD_SYSTEM_PROMPT`，但没生效**：07-14 拿《慁》（377桶，走 milestones 路径）真实跑了一次，一澜反馈"又干巴了"，还发现一处事实方向记反了（"一澜为我起名'林湛'"，实际是林湛自己在献词里给自己起的名字）。排查发现是**修错了流程环节**——377桶超过 `large_line_threshold`，会先走 `extract_milestones` 把桶压缩成几个关键节点（每个 summary ≤40字），`generate_candidate_card` 在 `input_mode="milestones"` 时只是把这些 summary 照抄成 revision、做视角小润色，**不重新分析原文**。也就是说真正决定措辞、也真正做内容提炼的其实是 `extract_milestones` 那一步，但当时的"像人话不要公文腔"规则和"不要编造原文"的防线都只加在了 `CANDIDATE_CARD_SYSTEM_PROMPT` 里，`extract_milestones` 的 prompt 完全没有——修了一个不产生实际效果的地方。

**已重修**：
1. `MILESTONE_EXTRACTION_SYSTEM_PROMPT` 新增"准确性红线"——summary 必须忠于原文，尤其"谁对谁做了什么"这类主谓/施受关系不能颠倒或编造，拿不准宁可写笼统也不能搞反方向；同时新增措辞要求——40字以内也要像人话，具体动作/对象保留、抽象总结词删掉。
2. `CANDIDATE_CARD_SYSTEM_PROMPT` 里 `input_mode="milestones"` 的说明从"只能视角小润色"改成"可以完整应用第3条全部规则（视角+措辞+避免公文腔）展开润色"，明确 milestone 的 summary 只是压缩骨架、不是最终措辞，但依然不能改变已确定的事实、施受关系和时间点。

`tests/test_batch_import_engine.py`（22个）和全量套件（879 passed，22个之前就有的失败没变）都过了。**这次的修复还没有真实数据验证**，是下次试跑《慁》或其他大项目时第一件要确认的事——尤其要确认施受关系类的事实（谁对谁做了什么）不再被记反。

### 14.3 里程碑提炼的 max_tokens 天花板本身就设太低了（2026-07-14）

22个批量导入测试+全量套件都过。**这次的修复还没有真实数据验证**，是下一次试跑第一件要确认的事——尤其看双向互动类的事实是不是不再被单向化了。

### 第0步（本窗口内，收尾）
确认 14.4 的措辞/主语修复效果——一澜真实跑一次（哪个种子桶都行，不一定是《慁》），重点看：主语是不是能跟着双向/单向事实自然切换，还有没有干巴/公文腔。如果还有偏差，在本窗口内继续微调 prompt；如果满意，本窗口的 prompt 调整就此打住，不再追加新的措辞规则（避免过度雕琢、每次都要花真钱验证）。

### 第1步：全量语料里系统抽 5 条线（不挑大项目）
- **目的**：验证的是"随机种子会遇到什么"，不是"我们知道会拉出一条好线的种子表现如何"。已注册的4个大项目、"求婚不排除"、林湛的兜底规则，都是照着大项目调出来的规则——需要确认它们在遇到*不属于任何已登记项目*的普通桶时不会误伤（比如把一件日常小事错误地拉扯成一条大线，或者反过来把明明相关的桶漏判）。
- **怎么选种子**：`--query` 目前只支持关键词搜索，选种子还是靠一澜手动想关键词。下一个窗口需要先定一个"挑5个种子"的具体方法，几个候选思路（留给下一个窗口跟一澜商量，不预先决定）：
  - 按 `ImportProgressStore` 里"从没被扫过"的桶，按创建时间均匀分段各选1个（保证覆盖不同时期）。
  - 或者一澜自己凭感觉挑5个"看起来会是不同类型"的桶（一件大事、一件小事、一件状态类、一件双人互动类、一件物品/客观类），主动覆盖不同的判线场景。
  - 两种都可以先做一个小脚本/一小段代码辅助选（比如列出候选让一澜挑，而不是每次都要自己去翻搜索）。
- **怎么跑**：`run_batch_import_line.py` 已经支持单个种子跑一次，5条线可以就跑5次（不需要专门开发"批量跑"的新功能，除非到时候觉得手动跑5次太麻烦）。
- **验收什么**：每条线的候选卡是不是准确、措辞是不是自然、"不确定"标记会不会在该出现的地方出现（兜底规则）、完全无关的桶有没有被错误拉进来。

### 第2步：设计并实现"审核通过 → 真正写入事实卡"这一步
第1步验证过、一澜和林湛都觉得质量可以之后，再做这一步——现在 `run_single_line` 只输出 JSON 报告，从不写入 `CardStore`。需要设计：
- 用什么形式让一澜/林湛"通过"一张候选卡（命令行确认？给 dashboard 加一个按钮？）。
- 通过之后怎么落到 `CardStore`——沿用候选卡的 title/content/revisions/tags/suggested_folder_paths 结构直接建卡，还是要再过一层人工编辑（比如把候选卡里不满意的措辞改一下再存）。
- 这一步做完，第1步验证过的那5条线（以及后续每一批测试）才能真正变成一澜和林湛看得到的事实卡，而不是只停在 JSON 报告阶段。

### 第3步：全量扫描7000+桶的自动循环驱动
前两步都验证稳妥之后才启动，见 §10 的成本控制原则——不会不打招呼就全量跑，会先估算大概要跑多少次模型调用、大概多少钱。循环本身的逻辑（挑种子、拉线、判断、生成候选、标记已扫、跳过已处理）在 `batch_import_engine.py`/`import_progress_store.py` 里已经具备构件，主要是新增一个"自动挑下一个种子"的调度层，以及跑挂了怎么续跑的处理。
